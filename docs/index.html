A tiny inference engine you can actually read.

When you send a prompt to a language model, something has to run it. That something is an inference engine. It takes your words, feeds them through the model, and sends new words back, one piece at a time. nanoserve is one of these engines, written small on purpose so you can learn how the big ones work. This page walks through its four main ideas.

1. Two phases: prefill and decode

Generating text has two phases. First comes prefill. The engine reads your whole prompt in one big step. Every word is processed at the same time, because they are all already known.

Then comes decode. The model writes its answer one token at a time. A token is a chunk of a word, the small piece of text the model actually thinks in. Each new token depends on all the ones before it, so this part cannot be parallel. It is a loop.

The math behind this

The core operation is attention. Each token compares itself with every token before it:

\[ \mathrm{attention}(Q, K, V) = \mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}\right) V \]

Dividing by $\sqrt{d}$ keeps the scores from exploding as the head size $d$ grows. Without it, the softmax would squash into one hot guesses.

Now count the comparisons. Prefill of a prompt with $P$ tokens: every token attends to every earlier one, so the work grows like $P^2$. It is one big parallel step.

Decode is different. Token $n$ only needs one new row of comparisons against the $n$ tokens already in the cache. Cheap per step, but strictly one token at a time. Writing $T$ tokens after a prompt of length $P$ costs

\[ \sum_{n=P}^{P+T-1} n \;=\; \frac{(P+T)(P+T-1) - P(P-1)}{2} \]

sequential little steps that no machine can parallelize away. That is why decode speed, not prefill speed, decides how fast words appear on your screen.

2. The paged KV cache, or how memory is shared

Here is a problem. During decode, the model needs to remember every token it has seen so far. That memory is called the KV cache. You can think of it as the model's notebook. Old engines reserved a huge notebook for every request, just in case the answer got long. Most of those pages stayed blank. That is a lot of wasted memory.

nanoserve tears the notebook into small fixed-size pages called blocks. A sequence only gets a new block when its last one is full. The rule that keeps everything safe is simple: one block, one owner. No two sequences ever share a block.

The math behind this

How big is the notebook? Every token stores one key vector and one value vector at every layer of the model:

\[ \text{bytes per token} = 2 \times L \times H_{kv} \times d_{head} \times b \]

For Qwen3-0.6B: $L = 28$ layers, $H_{kv} = 8$ key/value heads, $d_{head} = 128$, and $b = 2$ bytes per number (bf16). That gives

\[ 2 \times 28 \times 8 \times 128 \times 2 = 114{,}688 \text{ bytes} \approx 112 \text{ KiB per token} \]

A 1000-token answer needs about 110 MiB. Old engines reserved space for the longest possible answer up front, so a short answer wasted most of its reservation.

Paging shrinks the waste, not the need. With blocks of $s$ slots, a sequence of $n$ tokens uses $\lceil n / s \rceil$ blocks, so it wastes at most $s - 1$ empty slots. Across $N$ sequences:

\[ \text{total waste} < N \times s \text{ slots} \]

instead of whole max-length reservations. The one block, one owner rule is what makes this safe: every slot is accounted for in exactly one place, and the demo above shows a block can never be double-booked.

3. Continuous batching: never let a seat stay empty

Real servers handle many requests at once. The naive way is static batching: group a few requests, run them together, and wait until every single one finishes before starting the next group. Short answers finish early and their seats sit empty, waiting for the slowest answer in the group.

Continuous batching fixes this. After every single token, the scheduler looks around. Finished a request? A waiting one takes its seat immediately, at the very next step. Press the button and watch both styles handle the same five requests.

The math behind this

Count the seats. A batch with $S$ seats running for $T$ steps spends $S \times T$ seat-steps. The useful work is the tokens actually generated:

\[ \text{efficiency} = \frac{\text{tokens generated}}{S \times T} \]

In the animation above, static batching holds 3 seats for 8 steps. That is 24 seat-steps to produce 15 tokens, an efficiency of $15/24 \approx 63\%$. Continuous batching spends only 17 seat-steps on the same 15 tokens, about $88\%$, because no seat is ever held by a finished request.

The gap grows with the variance of answer lengths. Real traffic has huge variance, which is why every serious engine batches continuously.

4. Preemption: what happens when memory runs out

Imagine every block is taken and a running sequence needs one more. Someone has to give up their seat. nanoserve evicts the youngest running sequence, the one that arrived most recently. That choice is deliberate. The youngest sequence has done the least work, so the least is lost.

Eviction is not deletion. The sequence keeps all its tokens. Only its memory blocks are freed. It goes to the front of the waiting queue, ahead of brand new requests, because it already did work once. When space opens up, it prefills again from the start. This is called preemption.

You can see it happen in the block demo above. Add sequences until the memory is full, add one more, and run a step. The youngest sequence's blocks will flash free and its chip will jump to the front of the queue with a red badge.

The math behind this

Eviction is not free. The victim must redo its prefill later, and prefill of $n$ tokens costs about $n^2$ attention work. To lose as little as possible, evict the sequence with the fewest computed tokens:

\[ \text{victim} = \arg\min_{s \,\in\, \text{running}} n_s \]

The youngest running sequence is almost always that sequence, because it has had the fewest decode steps. One cheap rule that is close to optimal, with no extra bookkeeping. The queue jump matters too: the victim already paid its prompt cost once, so it re-enters ahead of requests that have paid nothing.

5. How we know it is correct

A fast engine that says the wrong words is worthless. So nanoserve is checked against HuggingFace, the reference library everyone trusts. The test loads the exact same model weights into both engines, gives both the same prompt, and lets each one write 50 tokens greedily, always picking its most likely next token.

The answers must match token for token. Not similar. Identical numbers, all 50 times. Here is a real example with a real model (Qwen3-0.6B). Both engines produce exactly this, in exactly this order:

prompt: "The capital of France is"

Paris12095 .13 The576 capital6722 of315 France9625 is374 also1083 the279 capital6722 of315 the279 Republic5429 of315

HuggingFace: these ids. nanoserve: these same ids. Every new idea on this page is only allowed in if this test keeps passing. That is what makes the small engine trustworthy.

The math behind this

The engine serves models in bf16, a 16-bit number format with only 8 bits of mantissa. The gap between two neighboring bf16 numbers near a value $x$ is about

\[ \text{step}(x) \approx x \times 2^{-8} \approx 0.004\,x \]

Model logits sit near 25, so neighbors are about $0.1$ apart. Two perfectly correct implementations that round in a different order can disagree by a few of these steps on every logit. Comparing raw numbers with a tight tolerance would fail even when nothing is wrong.

What must match is the decision, not the exact score. The largest logit picks the next token, so the test pins

\[ \arg\max_i \ell_i^{\text{nanoserve}} \;=\; \arg\max_i \ell_i^{\text{HF}} \]

at every position, plus a 50-token decode where both engines must emit identical ids. Rounding may wiggle the scores. It may never change the answer.
